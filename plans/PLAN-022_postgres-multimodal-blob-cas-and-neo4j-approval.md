## 1. Context & Architectural Motivation

An architectural review of `platform-engramory` and `platform-technology_stack` evaluated two foundational capabilities for multimodal agent knowledge and graph retrieval:

### 1.1 PostgreSQL-First Multimodal Blob & Large-Video (`20 GB+`) Content-Addressable Store (CAS)

1. **Multimodal Retrieval vs. Raw Binary Storage:**
   - `platform-engramory` stores canonical text, `vector(1536)` HNSW embeddings, and `tsvector` BM25 indexes in PostgreSQL (`kb_documents`, `kb_sections`, `episodes`, `memories`).
   - Multimodal ingestion (PDFs, images, audio, and videos up to `20 GB+`) converts media into text/Markdown descriptions, transcripts, and frame captions before embedding into `vector(1536)`, while optionally retaining raw binary blobs for visual citations, runbook screenshots, and future re-extraction.
2. **Eliminating Unnecessary External Object Storage Dependencies:**
   - Previously, `platform-technology_stack` Decision `D14` (`05-database-stack.md:52`) and Specification `22` (`22-hybrid-s3-object-storage-seaweedfs-and-cloudflare-r2.md:73-86`) required any payload `> 256 KiB` to be offloaded to an external S3-compatible bucket (OCI Object Storage / Cloudflare R2), while self-hosted S3 emulators were retired.
   - Storing raw blobs inside PostgreSQL 18 avoids operating a separate storage plane, preserves single-database transactional/tenant boundaries (`tenant_id`), and leverages SHA-256 content-addressable deduplication—provided large blobs (`50 MiB` to `20 GB+`) do not pollute hot OLTP tables (`kb_sections`, `memories`, `xp.ledger`), evict `shared_buffers`, saturate `pg_wal` / `pgBackRest`, starve `PgBouncer` transaction pools, or exceed PostgreSQL's `1 GB` `varlena` (`bytea`) field limit.
3. **5-Control PostgreSQL `20 GB+` Chunked Blob CAS Architecture (Refined Rule `D14a` / `D14b`):**
   - **Rule `D14a` (Hot Table & Queue Envelope Limit — `256 KiB`):** Hot relational/vector tables (`xp.ledger`, `kb_sections`, `memories`) and NATS JetStream / OTel span payloads never inline binary or text blobs `> 256 KiB`; they carry only `uri` (`pgblob://<tenant_id>/<sha256>`, `s3://...`, or `file://...`) and `sha256`.
   - **Rule `D14b` (Approved Artifact & Blob Store Backends):** Services may implement `StoragePort` using either **PostgreSQL Chunked Content-Addressable Storage (`PgBlobStorageAdapter`)**, **OCI Object Storage S3 API** (with Cloudflare R2 secondary), or **`LocalFsBackend`** (offline tests), governed by five mandatory PostgreSQL controls for large media (`20 GB+`):
     1. **Dedicated Cold Tablespace (`ts_blob_cold`) & Cloud PG Fallback:** `CREATE TABLESPACE ts_blob_cold LOCATION '/var/lib/postgresql/blob_ts'` (mounted as a dedicated host volume outside `PGDATA`, `chown postgres:postgres`, mode `0700`) with `seq_page_cost = 1.0`, `random_page_cost = 1.1`, `effective_io_concurrency = 256`, and `maintenance_io_concurrency = 128`, isolating bulk sequential media I/O from `pg_default` OLTP and `pgvector` HNSW indexes. On managed cloud PostgreSQL (GCP Cloud SQL, AlloyDB, Azure Flexible Server) or ephemeral CI containers without `SUPERUSER` tablespace privileges, migration `0010_postgres_blob_cas.sql` uses a conditional `DO $$` block that checks `pg_tablespace` and falls back cleanly to `pg_default`.
     2. **Dedicated Manifest & Tiered `4 MiB` Chunk Tables (`kb_blobs`, `kb_blob_chunks`, `kb_blob_chunks_large`):**
        - `kb_blobs (tenant_id, sha256, content_type, byte_size, chunk_size, chunk_count, storage_tier, status, metadata, created_at, PRIMARY KEY (tenant_id, sha256))` in `pg_default` (`status IN ('uploading', 'ready', 'failed')` prevents partial readers during streaming ingest).
        - `kb_blob_chunks (tenant_id, sha256, chunk_index, data BYTEA, PRIMARY KEY (tenant_id, sha256, chunk_index))` (`LOGGED`, `TABLESPACE ts_blob_cold`) for documents, images, and clips `<= 50 MiB` (covered by continuous 5-minute `pgBackRest` WAL PITR).
        - `kb_blob_chunks_large (tenant_id, sha256, chunk_index, data BYTEA, PRIMARY KEY (tenant_id, sha256, chunk_index))` (`UNLOGGED`, `TABLESPACE ts_blob_cold`) for large videos and media archives `> 50 MiB` up to `20 GB+` (`5,120 x 4 MiB` chunks per `20 GB` video, capped by `MAX_BLOB_BYTES = 25 GiB`). Both chunk tables intentionally omit per-row foreign keys to `kb_blobs` to avoid `5,120` `FOR KEY SHARE` trigger locks against `kb_blobs` during `COPY BINARY` and because PostgreSQL prohibits foreign keys between `LOGGED` and `UNLOGGED` tables; orphan chunks from aborted uploads are cleaned up in the upload `except:` handler, on `delete()`, and via a periodic sweep (`status IN ('uploading', 'failed') AND created_at < now() - interval '2 hours'`).
        - **`UNLOGGED` Crash-Truncation Recovery & Read-Time Completeness Guard (`[C2]`):** Bypassing `pg_wal` eliminates `2x` WAL write amplification (`40 GB` disk writes per `20 GB` video), checkpoint I/O stalls, and `pgBackRest` 60-second WAL archive queue saturation. An immediate post-upload `CHECKPOINT` flushes dirty `UNLOGGED` pages for clean restarts (`pg_ctl stop -m fast/smart`), and a daily non-recompressing dump (`pg_dump -d engramory --format=custom -Z 0 -t public.kb_blob_chunks_large | zstd -1 -T0 | age`) replicates across `B0` -> `B1` -> `B2a` -> `B2b` (`28-backup-and-disaster-recovery-strategy.md`). Because PostgreSQL 18 overwrites all `UNLOGGED` relations with their empty `_init` fork on any **unclean** shutdown (`SIGKILL`, OOM, host power loss) while `LOGGED` `kb_blobs` retains `status = 'ready'`, two guards prevent split-brain 0-byte reads: (a) post-crash recovery restores `kb_blob_chunks_large` from the latest daily `B0` dump (`pg_restore -d engramory --data-only -t public.kb_blob_chunks_large`) and runs a reconciliation query setting `status = 'failed'` on any `storage_tier = 'unlogged'` manifest where `COUNT(chunk_index) < chunk_count`; and (b) `PgBlobStorageAdapter.get_stream()`, `get()`, and `exists()` verify both `kb_blobs.status = 'ready'` AND `COUNT(chunk_index) == kb_blobs.chunk_count` before serving bytes (raising `BlobIncompleteError` and marking `status = 'failed'` if truncated).
     3. **`STORAGE EXTERNAL` & `fillfactor = 100`:** `ALTER TABLE ... ALTER COLUMN data SET STORAGE EXTERNAL` disables redundant `pglz`/`lz4` CPU compression on pre-compressed media (`.mp4`, `.mkv`, `.png`, `.jpg`, `.pdf`) and packs immutable chunk pages at 100% density.
     4. **`BAS_BULKWRITE` `16 MiB` Ring Buffer (`COPY BINARY`), Direct `:5432` Pool & Bounded Keyset Reads (`[M1]`, `[M2]`):**
        - **Direct `:5432` Streaming Pool (`[M1]`):** `PgBlobStorageAdapter` uses a bounded direct PostgreSQL `:5432` connection pool (`max_size = 4`, `autocommit = True` for post-upload `CHECKPOINT` via `GRANT pg_checkpoint TO engramory`) rather than `PgBouncer` `:6432` (`pool_mode = transaction`), avoiding `PgBouncer` transaction-pool starvation and `CHECKPOINT cannot run inside a transaction block` errors.
        - **Write Path (`BAS_BULKWRITE`):** Streaming `4 MiB` chunks via `psycopg` v3 `COPY ... FROM STDIN WITH (FORMAT BINARY)` activates PostgreSQL's `16 MiB` `BAS_BULKWRITE` buffer access strategy across both the main heap and TOAST (`toast_save_datum`), preventing `shared_buffers` eviction of `pgvector` HNSW graphs and verifying `computed_sha256 == expected_sha256` before setting `kb_blobs.status = 'ready'`.
        - **Read Path (Bounded Keyset Cursor + Clock-Sweep `usage_count = 1`):** Because PostgreSQL only applies `BAS_BULKREAD` to `SeqScan` (never to `IndexScan` or `pg_toast` lookups), `get_stream()` reads via bounded keyset pagination (`WHERE tenant_id = $1 AND sha256 = $2 AND chunk_index >= $3 ORDER BY chunk_index ASC LIMIT 4`, bounding backend/client RAM to `16 MiB`), while TOAST pages enter `shared_buffers` with clock-sweep `usage_count = 1` so they are evicted before hot HNSW vector index pages (`usage_count = 5`).
     5. **PostgreSQL 18 Server Tuning (`postgresql.conf`):** `max_wal_size = 32GB`, `min_wal_size = 4GB`, `checkpoint_timeout = 30min`, `checkpoint_completion_target = 0.9`, `wal_compression = zstd`, `wal_init_zero = off`, `io_combine_limit = 128kB`, and `vacuum_buffer_usage_limit = 16MB`.

### 1.2 Approving Neo4j (`Adopt`) Alongside PostgreSQL as a First-Class Graph Engine

1. **Resolving Policy vs. Deployment Drift:**
   - Previously, `05-database-stack.md` (`D17` at line 55, table row at line 228, and §6.13 at lines 665–701), `00-architecture-summary.md` (§4.14 at line 329), `07-review-findings.md` (Finding 17 at lines 227–230), and `23-federated-graph-lake-embedded-kuzu-and-central-graphdb.md` (§4 & §8) classified **Neo4j** as an "Exception-Only" store requiring a special architectural exception gate.
   - In reality, `stage-neo4j` (`neo4j:5.26-community`) is already deployed on `stage`, backed up daily via `tar --zstd + age snapshot of platform-data_neo4j (neo4j-$STAMP.tar.zst.age)` in `28-backup-and-disaster-recovery-strategy.md:81`, and implemented as a first-class adapter in `platform-engramory` (`Neo4jGraphAdapter` in `src/engramory/adapters/dev/graph_neo4j.py`, `ADR-03_graph_engine.yaml`, `PLAN-006`).
   - Furthermore, as documented in `ADR-03_graph_engine.yaml:20-35`, managed Apache AGE is unavailable on GCP Cloud SQL and AlloyDB, whereas Neo4j (Community self-hosted / Neo4j Aura) is cloud-portable across OCI, GCP, and Azure.
2. **Updated Decision `D17` (PostgreSQL + Neo4j Approved Dual-Engine Graph Standard):**
   - **PostgreSQL 18** (`graph_entities`, `graph_relations`, recursive CTEs, or Apache AGE) and **Neo4j** (`neo4j:5.26-community` / `stage-neo4j` / Neo4j Aura via Bolt `:7687` and Python `neo4j>=5.26.0` driver) are **both approved (`Adopt`) graph engines**, used as needed without requiring an architectural exception.
   - **Rebuildable Projection Invariant (`ADR-01` / `ADR-03` / `ADR-05`):** PostgreSQL 18 remains the single canonical system of record for entities, relationships, and provenance; Neo4j operates behind `GraphPort` as a rebuildable property-graph projection for multi-hop Cypher traversal, SDD lineage, blast-radius analysis, entity network exploration, and hybrid GraphRAG.
